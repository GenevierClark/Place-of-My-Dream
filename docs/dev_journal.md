## [Day 2] 2026-07-22 — Room 클래스 계층 설계

### 1. 상속(다형성) vs enum class + switch

**질문**: 방 종류(휴식처/전투방/상점/잠긴 문)를 구분할 때, `Room`을 상속하는 서브클래스로 나눌지 아니면 `Room` 하나에 타입을 나타내는 `enum class` 필드를 두고 `switch`로 분기할지 고민.

**논의 내용**:
- **가상 함수(다형성)**: 새 방 종류를 추가할 때 새 클래스 하나만 만들면 끝. 기존 호출부 코드를 안 건드려도 됨 (Open/Closed 원칙).
- **enum class + switch**: 방 종류가 늘어날 때마다 그 타입을 다루는 모든 switch문을 찾아 case를 추가해야 함. 하나라도 빠뜨리면 조용히 버그가 됨. 대신 방 개수가 적을 땐 로직이 한 함수에 모여 있어 한눈에 보기 편함.

**결론**: `CLAUDE.md`에 "다형성을 활용한 유연한 노드 클래스 구조"가 포트폴리오 목표로 명시되어 있어서, 상속 + 가상 함수 방식으로 결정. `Room`을 추상 클래스로 만들고 `RestArea`/`BattleArea`/`StoreArea`가 상속받는 구조로 확정.

### 2. `Room::neighbors`를 `Room*`(raw pointer)로 둔 이유

`std::vector<Room*> neighbors`가 raw pointer인 이유: 인접 노드는 "소유(owning)"가 아니라 "참조(non-owning)"만 하는 관계이기 때문. 소유권은 나중에 만들 `Map`류의 컨테이너가 가지게 될 예정. `shared_ptr`을 쓸 필요가 없는 전형적인 경우.

### 3. `EnterEvent()` 함수의 반환값 설계 — 여러 번 시행착오를 거침

**1차 시도**: `virtual void EnterEvent() = 0;` — 매개변수도 반환값도 없었음.

**2차 시도**: 매개변수로 `Player*`를 받는 걸 고려. → 이 과정에서 "Player를 안 받고 방에 들어가는 상황이 있을 수 있나?"를 자문하고, 없다면 포인터보다 참조(`Player&`)가 "항상 유효한 대상이 필요하다"는 계약을 타입만으로 드러낼 수 있다는 걸 이해함. `Player&`로 확정.

**3차 시도 — 반환 타입**: "전투 로직은 따로 작성할 거니까" 반환 타입을 `bool`로 바꿈. 처음엔 "이벤트가 온전히 실행됐는가"라는 의미로 생각했으나, 리뷰 과정에서 "함수가 호출되면 내부 로직은 예외 없이 항상 끝까지 실행되는데, 그럼 언제 `false`가 되는 거지?"라는 질문에 막힘 — 이 의미는 폐기.

**4차 시도 (최종)**: "이 방에서 할 수 있는 행동이 모두 끝났는가"라는 의미로 재정의. 이건 `Room`에 이미 있던 `isVisited` 필드와 개념이 같다는 걸 발견 — `EnterEvent()`가 `true`를 반환하면 호출부가 `SetisVisited(true)`를 호출하는 식으로 연결하기로 함.

**추가로 나온 중요한 질문**: "메인 루프가 `true`를 받았을 때, 이게 전투방이었는지 상점이었는지 어떻게 알고 그에 맞는 다음 행동(전투 시작/상점 열기)을 할까?" → 답: **몰라도 된다.** 다형성을 쓰는 이유 자체가 "호출하는 쪽이 구체 타입을 몰라도 되게 만들기 위해서"이므로, "전투를 시작하는 로직"이나 "상점을 여는 로직" 자체를 메인 루프가 아니라 **`BattleArea::EnterEvent()`/`StoreArea::EnterEvent()` 내부에서 직접 처리**하도록 설계 방향을 정함. `bool`은 그저 "이 방의 상호작용이 끝나서 `isVisited`로 전환해도 되는가"만 나타내는 최소한의 신호로 남기로 함.

**최종 계약**:
```cpp
virtual bool EnterEvent(Player& _player) = 0;
// 반환값 의미: 이 방에서 할 수 있는 행동이 모두 끝났는가 (→ true면 호출부가 isVisited를 true로 설정)
// 전투/상점 등 구체적인 처리는 각 서브클래스의 override 내부에서 완결
```

### 4. `RestArea`/`BattleArea`/`StoreArea` 초기 구현 리뷰 — 발견된 버그들

**버그 1: 입력을 while 루프 밖에서 한 번만 받음 (무한루프)**
```cpp
int action;
cin >> action;        // 딱 한 번만 입력받음
while (true) {
    switch (action) {  // action 값이 안 바뀜
        case 1: ... break;  // switch만 빠져나가고 while은 계속 돎
```
`break`는 `switch`문만 빠져나가지 `while` 루프는 안 빠져나간다는 점을 놓쳐서, 1번이나 2번을 선택하면 같은 case가 무한 반복 실행됨. `cin >> action;`을 `while(true)` **안으로** 옮겨서 해결. (`RestArea`, `BattleArea`에서 발생, `StoreArea`는 처음부터 올바르게 작성됨.)

**버그 2: `StoreArea`의 "Exit" 선택지가 실제로 종료 안 됨**
```cpp
case 3:
    cout << "Exiting Store..." << endl;
    break;   // switch만 빠져나가고 while(true)은 안 끝남
```
메시지만 찍고 다시 메뉴로 돌아감. `return`을 써야 함수가 실제로 끝난다는 걸 놓친 케이스. `return false;`로 수정.

**버그 3: 루프 뒤의 도달 불가능한(dead) `return`**
```cpp
while (true) {
    ...
    case 3: return false;
}
return false;  // 여기 도달할 방법이 없음 (컴파일은 되지만 죽은 코드)
```
`while(true)`을 빠져나가는 유일한 경로가 `case`문 안의 `return`뿐이라, 루프 뒤의 `return`은 죽은 코드. 나중에 `case 1`/`2`도 각각 자기 로직이 끝나는 지점에서 바로 `return true;`하도록 구조를 정리하면서 자연스럽게 사라짐.

**버그 4: `RestArea::ApplySleepDepthRecovery`/`ApplyHealthRecovery`가 선언만 있고 구현이 없음** — `Player` 클래스가 아직 없어서 발생한 문제. `Player` 클래스를 만들기 전까지는 링커 에러(undefined reference) 상태로 보류됨.

**깨달음**: 이 과정에서 `switch`문의 `break`가 정확히 무엇을 빠져나가는지(그 `switch`문 자체만, 바깥의 반복문은 아님)에 대한 이해가 부족했다는 걸 스스로 인지함. 이후 `case`마다 로직이 끝나는 즉시 `return`으로 함수를 종료하는 패턴으로 정리하면서 문제가 해결됨.

## [Day 3] 2026-07-26 — Player 클래스 설계 및 RestArea 실제 구현

### 5. `std::enable_shared_from_this` 상세 설명 (이전 Text RPG 프로젝트의 `Character` 클래스 리뷰 중)

**왜 `this`를 그냥 `shared_ptr`로 감싸면 안 되는가**:
```cpp
std::shared_ptr<Character> GetSelf() {
    return std::shared_ptr<Character>(this); // 절대 하면 안 됨
}
```
이렇게 하면 원래 이 객체를 가리키던 `shared_ptr`의 컨트롤 블록과 무관한, **완전히 새로운 컨트롤 블록**이 생성됨. 참조 카운트가 0이 되는 시점이 두 번 발생해서 같은 메모리를 두 번 `delete` → 크래시.

**`enable_shared_from_this`의 동작 원리**: 이걸 상속하면 내부에 숨겨진 `weak_ptr` 멤버가 생김. `std::make_shared<T>(...)`나 `shared_ptr<T>(new T(...))`로 객체를 최초로 감쌀 때, 그 컨트롤 블록 정보가 이 내부 `weak_ptr`에 자동 연결됨. 이후 `shared_from_this()`는 내부적으로 `internal_weak_ptr.lock()`을 호출하는 것과 같아서, 컨트롤 블록이 중복 생성되지 않음.

**핵심 함정**: 생성자 내부에서는 아직 어떤 `shared_ptr`도 이 객체를 소유하지 않은 상태라, `shared_from_this()`를 호출하면 `std::bad_weak_ptr` 예외 발생. (Text RPG 프로젝트에서 `InitComponent()`를 생성자와 분리했던 이유가 바로 이것.) 마찬가지로, `shared_ptr`로 감싸지 않은 객체(스택 객체, 그냥 `new`로 만든 객체)에 대고 호출해도 동일하게 터짐.

**Place of My Dream 적용 여부**: 지금 `Room`이 `Player&`를 참조로만 받는 구조라 당장은 `enable_shared_from_this`가 필요 없음. `Player`의 소유권을 어떻게 관리할지(예: 중앙 매니저가 `shared_ptr`로 소유)는 아직 미정.

### 6. 게임 전체 구조 — 중앙 매니저 vs 탈중앙화

**질문**: 지금 만드는 게임 구조에서 이전 프로젝트의 `GameManager`처럼 중앙에서 관리하는 클래스를 둘지, 아니면 각자 관리하게 할지.

**논의 내용**:
- **중앙 매니저(Owner) 패턴**: 하나의 클래스가 플레이어/맵/진행 상태를 다 들고 메인 루프를 굴림. 상용 게임에도 `GameMode`, `GameInstance` 등으로 거의 항상 존재. 특히 로그라이크는 "현재 Run의 상태"를 한 곳에서 관리하는 게 자연스러워 흔한 패턴.
- **탈중앙화**: `MapManager`, `CombatManager`처럼 도메인별로 나눠 느슨하게 협력. 결합도는 낮아지지만 설계 난이도가 올라감. 팀/대규모 프로젝트에 적합, 30일 솔로 프로젝트엔 오버엔지니어링 가능성.

**결론**: 중앙 매니저 방식으로 진행하기로 함. 단, 이전 프로젝트에서 `GameManager`/`ItemDataManager`/`EnemyDataManager`를 전부 Singleton으로 만들었던 것에 대한 리뷰 피드백(전역 상태가 퍼지면 추적이 어려워짐)을 참고해서, 이번엔 Singleton이 아니라 `main()`에서 지역 변수로 소유하는 형태를 고려 중 (아직 확정은 아님, 실제 구현 시 다시 판단 예정).

### 7. 캐릭터 스탯의 자료형 선택

**질문**: HP/ATK/DEF 같은 스탯을 지금까지 `int`로만 써왔는데, 게임 구조에서 보통 어떤 자료형을 쓰는지.

**논의 내용**:
- `int`가 실제로 가장 흔함 — 지금까지의 방식이 틀린 게 아님.
- 고정 폭 정수 타입(`int32_t`, `int16_t` 등, `<cstdint>`)은 크기가 플랫폼에 상관없이 고정됨. `game_design.md`에 적힌 "구조체 메모리 패딩/정렬 최적화", 이진 직렬화(세이브 파일) 목표와 직결되는 선택지 — 나중에 세이브/직렬화를 본격적으로 다룰 때 고려하기로 함.
- `float`/`double`은 크리티컬 확률, 데미지 배율처럼 소수점이 필요한 값에만 쓰고, HP처럼 플레이어가 직접 보는 핵심 스탯은 정수로 유지하는 게 일반적 (부동소수점 비교/반올림 문제 회피).
- `unsigned int`의 함정: HP가 논리적으로 음수가 안 된다고 해서 `unsigned`로 하면 위험함 — `Health - Damage`에서 `Damage`가 `Health`보다 크면 음수로 안 내려가고 매우 큰 양수로 wrap-around됨. 그래서 계산 중간에 음수를 거칠 수 있는 값은 부호 있는 `int`로 두고, 0 이하가 되면 별도로 클램프하는 방식이 일반적.

**결론**: 지금은 `int`로 계속 진행, 세이브/직렬화 단계에서 고정 폭 타입 전환을 고려.

### 8. 참조를 지역 "별명"으로 쓰는 기법

**질문**: 변수명은 명확성을 위해 길게 짓고 싶은데, 매번 긴 이름을 쓰기 번거로우니 별명을 붙이는 기법이 있는지.

**답변 요지**:
```cpp
void SomeFunction() {
    int& hp = Health;  // Health의 지역 별명
    hp = 100;          // Health = 100;과 동일한 효과
}
```
`int& hp = Health;`는 새 변수를 만드는 게 아니라 `Health`를 가리키는 또 다른 이름을 만드는 것. 그 함수/스코프 안에서만 유효한 지역적 별명이라, 멤버 변수의 "공식 이름"(`Health`)은 명확하게 유지하면서 반복 사용은 짧게 할 수 있음.

**아닌 것들**: `using` 타입 별명(`using HP = int;`)은 **타입**에 붙는 것이지 **변수**에 붙는 게 아니라서 이 문제를 해결 못함. `#define` 매크로도 기술적으론 가능하지만 스코프 개념이 없어 부작용이 많아 현대 C++에선 지양.

### 9. `Character`/`Player` 클래스 구현 리뷰 — 초기화 누락 버그

**1차 작성본의 문제**:
```cpp
class Character {
private:
    int MaxHealth;   // 생성자가 없어서 초기화가 안 됨
    int Health;
    int AttackPower;
    int Defense;
public:
    int GetMaxHealth() const { return MaxHealth; }
    // SetMaxHealth()가 아예 없음 — 값을 넣을 방법 자체가 없었음
    ...
};
```
`Player()` 생성자에서 `SetHealth(100), SetAttackPower(1), SetDefense(0);`으로 세팅했지만, `MaxHealth`와 (`Player`의) `MaxSleepDepth`는 어디에도 초기화되는 곳이 없어서 **쓰레기 값**으로 남아있었음. `MaxHealth`는 setter조차 없었고, `MaxSleepDepth`는 getter/setter가 아예 둘 다 없었음. `game_design.md`상 "단련: Max HP 증가", "층 클리어마다 수면 심도 최대치 확장" 같은 핵심 기능에 쓰일 값들이라 실질적인 버그로 판단.

**추가로 발견된 것 — 콤마 연산자 오용**:
```cpp
SetHealth(100), SetAttackPower(1), SetDefense(0);
```
세미콜론 세 개로 나눈 것처럼 보이지만 실제로는 **콤마 연산자**로 묶인 하나의 문장. 세 함수가 순서대로 호출되긴 해서 결과적으로는 작동했지만, 콤마 연산자는 다른 문맥에서 예상치 못한 동작을 유발할 수 있는 함정 — 의도한 게 아니라면 세미콜론으로 나누는 게 맞다는 피드백.

**설계 선택지 논의 — 생성자로 초기화 vs setter 호출**: `Character`의 멤버가 전부 `private`이라 `Player`가 초기화 리스트에 직접 못 넣는 상황. 대안으로 `Character(int _health, int _atk, int _def)`처럼 매개변수 생성자를 만들고 `Player() : Character(100, 1, 0), ... {}`처럼 위임하는 방식을 제시. "생성자 위임 방식은 필수 스탯 없이는 객체를 만들 수 없다는 걸 타입 시스템 차원에서 강제해서, 지금 겪은 것 같은 초기화 누락 실수를 원천적으로 방지한다"는 게 핵심 장점.

**최종 수정본**:
```cpp
// Character.h
Character(int _maxhealth, int _atk, int _def)
    : MaxHealth(_maxhealth), Health(_maxhealth), AttackPower(_atk), Defense(_def) {}

// Player.h
Player()
    : Character(100, 1, 0), MaxSleepDepth(100), SleepDepth(100), Money(0) {}
```
생성자 위임 방식으로 변경, `SetMaxHealth()`/`MaxSleepDepth` getter·setter 추가. `Health(_maxhealth)`로 시작 체력을 최대 체력과 같게 설정한 것도 자연스러운 설계로 확인됨.

### 10. 포인터 vs 참조 — 실제 매개변수 설계에 적용

**질문**: `Room::EnterEvent`류 함수에서 `Player&`(참조)로 원본을 받아왔는데, 포인터로 주소를 받는 것과의 차이가 궁금함.

**핵심 차이 3가지**:
1. **null이 될 수 있는가**: 포인터는 `nullptr` 가능(대상이 없을 수 있음을 타입으로 표현). 참조는 한번 초기화되면 반드시 유효한 객체를 가리켜야 함 — "이 함수엔 항상 유효한 대상이 들어온다"는 계약을 표현할 때 적합.
2. **재바인딩(다른 대상으로 바꿔치기) 가능한가**: 포인터는 나중에 다른 객체를 가리키도록 재할당 가능. 참조는 한번 묶이면 스코프가 끝날 때까지 절대 다른 객체로 안 바뀜 (`ref = other;`는 재바인딩이 아니라 값 복사 대입임에 주의).
3. **호출부 코드의 명확성**: `Foo(&player)`는 `&`로 "이 함수가 원본을 바꿀 수도 있다"는 걸 눈에 띄게 알려줌. `Bar(player)`는 겉보기엔 값 전달처럼 보여서, 참조 매개변수는 안 바꿀 거면 `const`를 붙이는 관례가 있음.

**Place of My Dream에서의 판단**: "Player는 하나뿐이고 게임 진행 중엔 항상 존재하니, 방에 들어갔을 때 실행되는 함수들엔 반드시 유효한 Player가 있어야 한다"는 논리로 참조가 맞다고 스스로 결론 — 핵심 판단 기준은 **"이 함수가 호출되는 시점에 대상이 없을 수 있는가?"**임을 확인.

### 11. `const Player&`가 맞는지에 대한 오해 정정

**질문/오해**: "Player는 하나뿐이고 안 바뀌니까, `const Player&`로 선언하는 게 맞지 않을까?"

**정정 내용**: `const`는 "유일한 존재인가/안 바뀌는 대상을 가리키는가"가 아니라 **"이 함수가 참조를 통해 객체를 수정할 것인가"**를 나타내는 것. `RestArea::EnterEvent`나 `ApplySleepDepthRecovery` 같은 함수들은 결국 `_player.SetHealth(...)`처럼 상태를 직접 바꾸는 게 목적이므로, `const Player&`로 선언하면 `const`가 아닌 멤버 함수(`SetHealth` 등) 호출 시 컴파일 에러가 남.

**정리된 기준**:
- 읽기만 하는 함수(예: 상태 출력) → `const Player&`
- 상태를 바꾸는 함수(회복 로직 등) → `const` 없이 `Player&`

"참조 vs 포인터"와 "const 여부"는 서로 다른 기준(전자는 유효성/재바인딩, 후자는 수정 가능 여부)이라는 걸 명확히 구분해서 이해함.

### 12. `RestArea` 실제 구현 리뷰

**잘된 점**:
- `if(!GetisVisited())`로 재방문 시 다른 메뉴(퇴장만 가능)를 보여주는 처리 — "1회성 사용 후 빈 방" 설계를 정확히 구현.
- 이미 가득 찬 경우("Your sleep depth is already full") 안내 후 재선택 가능하게 만든 UX 처리.
- `case 4`(그냥 나가기)는 `isVisited`를 바꾸지 않아서, 나중에 다시 들어와 사용할 수 있도록 의도에 맞게 구현됨.

**지적된 문제**:
1. **`std::min` 사용 시 `<algorithm>` include 누락** — `Character.h`/`Room.h`/`Player.h`/`<iostream>` 어디에도 `<algorithm>`이 없는데 `std::min`을 씀. `InventoryComponent.h`의 `<memory>` 누락과 같은 패턴(우연히 컴파일되지만 이식성 없는 상태). → 수정 완료.
2. **`RestArea::ApplySleepDepthRecovery(...)`처럼 자기 클래스 멤버 함수를 클래스명으로 한정해서 호출** — 같은 클래스 안에서 호출하는 거라 불필요. `ApplySleepDepthRecovery(...)`만으로 충분. → 수정 완료.
3. **`game_design.md`와 실제 구현의 불일치 발견**: 문서엔 휴식처가 `[휴식: HP 30% 회복]` 또는 `[단련: Max HP +5]` 두 가지뿐인데, 실제 구현은 수면 심도 회복 / 체력 회복(정액) / 최대 체력 증가 세 가지. 확인 결과 세 선택지는 원래 기획된 내용이었고 문서에 옮기는 과정에서 누락된 것으로 확인. 체력 회복 방식(정액 vs 비율)은 아직 미결정. 구체적인 수치는 밸런스 조정 대상이라 문서에서 확정 수치 표기를 제거하고 미정으로 남기기로 함 → `game_design.md`/`devlog.md`에 반영.

### 13. `Monster` 클래스 상속 구조 설계 — 여러 차례 방향 전환

**최초 시도**: `Character -> Monster -> FloorMonster(Normal)`, `Character -> Monster -> FloorMonster(Elite)`처럼, 등급(Normal/Elite)을 상속 계층에 넣으려다 "난잡하다"고 느껴 막힘.

**막힌 이유 분석**: "Normal이냐 Elite냐"는 몬스터의 정체성(무엇인가)이 아니라 분류/등급(얼마나 강한가)에 가까운데, 상속 계층에 넣으면 "이 클래스가 곧 그 몬스터가 무엇인지"를 나타내는 의미가 되어버려서 실제 이름 있는 몬스터(예: "먼지 덮인 장난감 병정")가 들어갈 자리가 애매해짐.

**게임 스코프 관련 전제 확인**: 사용자가 "몬스터 수를 늘리기보다 하나하나의 질을 높이는" 방향(적은 수의 몬스터, 각각 고유 스킬/패턴)으로 가겠다고 밝힘. 이 전제는 구조 선택에 직접 영향을 줌 — 몬스터가 적고 각자 개성이 강하면, "데이터 테이블에서 스탯만 읽어와 재사용"하는 방식(이전 프로젝트의 `EnemyDataManager` 스타일)보다는 "몬스터마다 전용 클래스로 고유 로직을 직접 구현"하는 방식이 더 어울림 (이전 프로젝트의 `UndeadKnight::Attack` 오버라이드처럼).

**정리된 방향**: `Character -> Monster -> [구체 몬스터 이름]` (중간 등급 계층 없이 평평하게). `Monster`는 모든 몬스터 공통 요소(HP/ATK/DEF, 이름/설명, 드롭 재화, "이번 턴에 뭘 할지 결정"하는 공통 인터페이스)만 정의하고, Normal/Elite 같은 등급 구분은 상속이 아니라 `Monster`의 멤버(플래그 또는 enum)로 표현하기로 함.

**실제 작성된 `Monster.h` 리뷰에서 발견된 문제**:
1. **컴파일 에러**: 생성자 마지막이 `})`로 끝나 있었음 (`}`만 있어야 함) — 오타로 추정.
2. **타입명과 멤버명 충돌**: `struct DropTable { ... };`을 선언하고 멤버 변수도 `DropTable DropTable;`로 지음. C++에서 클래스 스코프 안에서 동일 이름을 다시 쓰면 이후로는 타입이 아니라 멤버(비-타입 개체) 쪽으로 우선 해석되는 규칙이 있어, 나중에 `Monster` 내부에서 `DropTable` 타입을 다시 언급해야 할 때 혼동을 유발할 수 있음. `Drops`처럼 다른 이름으로 바꾸는 게 안전하다는 피드백.
3. **드롭 재화 필드명(`DreamFragments`)이 당시 기획 용어("무의식의 잔재")와 안 맞았음** — 이후 V4.1 기획 개편에서 재화명 자체가 '무의식의 잔재' → **'꿈의 파편'**으로 바뀌면서, 결과적으로 `DreamFragments`라는 필드명이 오히려 새 기획 용어와 맞게 됨 (의도친 않았지만 우연히 해결됨).
4. **`Action()`이 매개변수 없는 순수 가상 함수였음** — 몬스터가 플레이어를 공격하려면 결국 대상이 필요하므로, `Room::EnterEvent(Player&)` 때와 같은 논리로 `Action(Player& _target)`처럼 대상을 받아야 하지 않겠냐는 질문을 던져둠 (아직 미해결, 사용자가 직접 결정할 부분).
5. **패턴 상태 추적 데이터(턴 카운터/발악기 발동 여부/고장남 상태)를 어디에 둘지** — "몬스터마다 완전히 다른 패턴"이라는 전제를 따르면 `Monster`(공통)가 아니라 각 구체 몬스터 클래스 안에 두는 게 일관적이라는 의견 제시 (아직 미해결).

### 14. 기획 변경(V4.1)이 진행 중인 코드에 미친 영향

기획이 V2.0 → V4.1로 개편되면서, 한창 스탯(HP10/ATK2/DEF0)과 AI 패턴("발악기"/"고장남" 등)까지 설계해뒀던 몬스터 "먼지 덮인 장난감 병정"이 새 몬스터 로스터(`[포근한 뱀 인형]`/`[거짓말을 하는 그림일기]`)에 이름이 없어짐. 확인 결과 개명/교체된 것으로 확인됐으나, 기존에 설계한 상세 스탯·패턴을 그대로 이어갈지 아니면 새로 부여된 감정 속성(망각/몽환)에 맞춰 다시 설계할지는 아직 결정되지 않음 — `Monster` 관련 코드를 계속 작업하기 전에 확인이 필요한 지점으로 `game_design.md` 12절에도 경고 문구로 남겨둠.

**교훈**: 기획이 유동적인 프로젝트에서는, 코드에 상세 스펙(구체적인 스킬명, 수치)을 옮기기 전에 "이 기획이 최종본인가, 아니면 계속 바뀔 여지가 있는가"를 먼저 가늠해보는 게 좋다. 지금처럼 기획 문서가 하루에도 여러 버전(V2.0 → V4.1)으로 개편될 수 있는 프로젝트에서는, 코드보다 문서 쪽이 먼저 안정화된 부분(예: 시스템 구조)부터 구현하고, 자주 바뀌는 부분(개별 몬스터 이름/수치)은 데이터로 분리해두면 나중에 개명/재설계가 있어도 코드 구조 자체는 덜 흔들릴 수 있음.

### 15. `Monster`/`CozySnake`/`Player` 완성까지 — 여러 라운드의 컴파일 에러·로직 버그 수정

`FirstFloorNormalMonster`(초기 시도)는 결국 삭제하고, `CozySnake`라는 이름의 새 구체 몬스터 클래스로 다시 작성함. 등급(Normal/Elite/Boss)과 속성(Lucid/Illusion/Oblivion)은 `GlobalSet.h`에 정의한 `enum`(스코프 없는 일반 enum)으로 처리 — `enum class`를 안 쓴 이유를 묻자, "이 이름들이 다른 곳과 겹칠 일이 딱히 없을 것 같고, 비교/연산이 더 편해서"라는 답변. 의도적인 트레이드오프 선택으로 존중하되, `Type`이라는 타입명 자체는 너무 흔해서 나중에 충돌 위험이 있다는 점만 참고로 남겨둠.

**발견하고 고친 컴파일 에러들**:
1. `FirstFloorNormalMonster::Action()`이 매개변수 없이 `override` — 베이스(`Monster::Action(Player&)`)와 시그니처가 달라 컴파일 에러. (→ 클래스 자체를 삭제하며 해결)
2. `FirstFloorNormalMonster`가 `Skill_1~3`을 하나도 구현 안 해서 여전히 추상 클래스였음. (→ 클래스 삭제로 해결)
3. `FirstFloorNormalMonster`의 생성자가 `Monster`의 예전 생성자 시그니처(문자열 2개를 받던 버전)를 그대로 호출하고 있어서, 현재 `Monster` 생성자(`int, int, int, int, MonsterRank, Type`)와 타입이 안 맞았음. (→ 클래스 삭제로 해결)
4. **`Player::SetHealth`가 `Character`의 `private` 멤버(`Health`, `MaxHealth`)에 파생 클래스에서 직접 접근하려 해서 컴파일 에러.** `private`는 파생 클래스에도 안 보인다는 걸 놓친 경우 — `protected`로 바꾸는 방법(A)과, `Character::SetHealth()`를 명시적으로 호출해서 값을 위임하는 방법(B) 중 B를 선택해 해결. (참고: 그 이후 클램핑 과정에서 `SetHealth(GetMaxHealth())`처럼 비한정 호출을 쓰면, 가상 함수라 `Player::SetHealth`가 한 번 더 재귀 호출되는데 — 이미 범위 안의 값이라 다음 호출에서 조건을 안 타서 무한루프는 안 되고 결과도 맞음. 다만 `Character::SetHealth(...)`로 명시적으로 부르는 게 더 직접적이라는 점은 참고로 남김.)
5. **`CozySnake.h`에서 오버라이드하려던 함수 이름이 잘못됨** — 베이스(`Monster`)엔 `virtual bool CheckSkillTrigger_1()`이 있는데, `CozySnake.h`엔 `void SetSkillTrigger_1() override;`로 선언(이름·반환타입 둘 다 다름). `override`가 매칭할 베이스 함수를 못 찾아 에러, 게다가 `.cpp`에 정의한 `CheckSkillTrigger_1`은 헤더에 선언조차 없어서 또 에러. `Check`로 이름을 맞춰서 해결.

**로직 버그 — 방어력 버프 무한 증가**: `CozySnake::Skill_3`(HP 50% 이하일 때 방어력 +2)에 처음엔 1회 제한이 없어서 조건을 만족하는 한 매 턴 무한히 증가하는 버그가 있었음. `Monster`의 `Skill_Trigger_1`(protected bool) + `CheckSkillTrigger_1()`로 "한번 조건을 만족하면 계속 true를 유지하는 래치" 방식으로 발동 여부를 추적하도록 수정. 다만 이 래치는 "완전히 1회만 발동"이 아니라 "그 이후로는 3턴 주기(`case 2`)마다 계속 발동"하는 구조라, 방어력 자체는 여전히 트리거된 이후 계속 쌓임 — 이건 실수가 아니라 **"HP 50% 이하부터는 영구적으로 방어 강화 페이즈에 들어간다"는 의도된 설계**임을 확인함 (이전에 설계했던 "장난감 병정"의 "1회만 발악 후 무력화"와는 다른, 별개의 의도적 패턴).

### 16. `BattleArea` 첫 구조 설계 리뷰

**컴파일 에러 — 존재하지 않는 함수 호출**: `BattleArea::BattleSequence`에서 몬스터 처치 보상 지급 시 `_player.SetDreamFragments(...)`/`GetDreamFragments()`를 호출했는데, 당시 `Player`엔 그 이름의 함수가 없고 `Money`라는 필드만 있었음 (재화 명칭이 기획상 '꿈의 파편'으로 바뀐 걸 반영 안 한 상태). 사용자가 직접 `Player`의 `Money` 필드 자체를 `DreamFragments`로 이름 변경 + getter/setter 추가하여 해결 — 컴파일 에러 해결과 동시에 `Monster`의 `DreamFragments` 필드명과도 명명이 통일됨.

**논의된 설계 포인트 — `RoomMonster`가 `nullptr`일 수 있는 문제**: 기본 생성자(`BattleArea()`)로 만들면 몬스터 없이 생성 가능해서, `GetRoomMonster()->...`가 널 포인터 역참조로 이어질 수 있었음. 사용자가 "게임 장르가 JRPG로 바뀌면서 맵이 고정 구조(Fixed Map)로 확정됐으니, 방을 만들 때 몬스터도 함께 고정으로 배치하는 게 맞다"고 스스로 결론 — 이미 확정된 기획(`game_design.md` 5절의 Fixed Map)과 정확히 연결지어 판단한 사례. 결론에 따라 기본 생성자를 아예 삭제하고 `BattleArea(Monster* _monster)`만 남겨서, "몬스터 없는 BattleArea"를 애초에 만들 수 없게 타입 레벨에서 차단함 (Character/Player 생성자 위임 때와 같은 패턴 — 필수 값을 생성자로 강제해서 실수를 원천 차단).

**미사용 함수 정리 — `SetReward()`**: 몬스터 처치 보상량을 나중에 바꾸는 용도로 만들어졌던 함수였으나, 실제로는 어디서도 호출되지 않았고 호출되면 오히려 `CozySnake` 생성자에서 이미 설정해둔 드롭량(5)을 하드코딩된 10으로 덮어쓰는 부작용이 있었음. 사용자가 "몬스터 생성 시점에 보상을 이미 다 설계해뒀으니 지금은 불필요하다"고 판단, 삭제하기로 함. 다만 "향후 보상이 재화뿐 아니라 장비/특수 아이템으로 확장되면 어떻게 설계할지"는 의미 있는 질문이라, 지금 당장 설계하지 않고(아직 아이템/인벤토리 시스템 자체가 없어서 추측성 설계가 될 위험) `game_design.md` TBD 목록에 메모만 남기고 아이템 시스템 설계 시점으로 미루기로 함 — 스코프 관리 관점에서 합리적인 판단.

**리뷰 중 추가로 발견한 것 — 코드/문서 속성 불일치**: `game_design.md`엔 [포근한 뱀 인형](`CozySnake`)이 망각(Oblivion) 속성으로 되어 있는데, 실제 `CozySnake.h` 생성자는 `Type::Illusion`(몽환)으로 되어 있어서 다른 몬스터([거짓말을 하는 그림일기])의 속성과 뒤바뀐 상태였음. 사용자가 `Type::Oblivion`으로 수정해서 문서와 일치시킴. (속성 상성 시스템 자체가 아직 미정이라 지금은 게임 동작에 영향 없지만, 나중에 상성 로직을 짤 때 헷갈릴 수 있어 미리 잡음.)

**공격 로직 미구현 확인**: `BattleSequence`의 `case 1: Attack`이 아직 실제 데미지 계산 없이 `IsTurnOver = true;`만 하고 있어서, 지금 상태로 플레이하면 몬스터를 절대 처치할 수 없음(몬스터의 턴은 이미 동작해서 플레이어만 피해를 입음). 사용자가 의도적으로 남겨둔 다음 작업 항목으로 확인 — 다음 세션에서 채울 예정.

## [Day 4 후속] 2026-08-03 — 데미지 계산, C++ 기본기(가상 함수/vtable/포인터·참조), 스킬 시스템 설계

### 17. 게임인재원 9기 준비라는 새 배경과, "억지로 끼워 넣지 않기" 원칙

사용자가 게임 관련 교육기관(게임인재원 9기, 2027년 초 입학 예정) 합격을 1차 목표로 삼고 있고, 자가진단으로 vtable/vptr(다중 상속 포함)과 템플릿+포인터/참조자 활용을 약점으로 파악했다는 배경을 공유함. 처음엔 이 두 주제를 이번 데미지 계산 기능에 의도적으로 녹여 넣고 싶어했으나("BattleArea 공격 데미지 계산 로직 구현에 vtable/다중상속, 템플릿 옵저버를 적용하고 싶다"), 논의 끝에 **억지로 끼워 넣지 않기로 결정**함.

- 감정 속성 상성 계산: 다형성/다중 상속 없이 그냥 일반 함수로 충분 — 상성 규칙은 모두에게 동일한 알고리즘이라 가상 함수가 필요 없음.
- 데미지 계산 자체: 가상 함수로 뽑아내는 게 자연스러움 (실제로 `Character::TakeDamageHealth`, `Monster::TakeDamageSleepDepth`로 구현됨).
- 전투 이벤트 알림(템플릿 옵저버): 지금 당장 필요하진 않아 보류, 필요해지면 그때 도입.
- 다중 상속: 지금 코드베이스에 진짜 필요한 지점이 안 보여서 도입하지 않기로 함. "다중 상속이 정당화되려면 보통 서로 다른 시스템이 같은 객체를 각자 다른 인터페이스로 다뤄야 하는 상황이 필요한데, 지금은 그런 상황이 없다"는 게 판단 근거.

**핵심 원칙으로 정리됨**: 기능을 하나씩 추가하면서 그 기능이 실제로 요구하는 기법을 자연스럽게 배우기 — 학습하고 싶은 기법을 먼저 정해놓고 기능에 끼워 맞추지 않기. (자세한 vtable/다중 상속 메커니즘 설명 — 단일 상속에서 vptr/vtable이 어떻게 런타임 디스패치를 하는지, 다중 상속에서 객체가 vptr을 여러 개 갖게 되는 이유, 포인터 조정(pointer adjustment)과 thunk, 다이아몬드 상속 문제와 virtual 상속의 비용, "순수 인터페이스 다중 상속"이 왜 안전한지 — 는 나눴지만 실제 코드에 적용은 보류.)

### 18. 데미지 함수 매개변수 설계 — 체력(Character&) vs 수면 심도(Player&)

체력 관련 데미지는 `Player`/`Monster` 둘 다 대상이 될 수 있어 `Character&`로 업캐스팅해서 받고, 수면 심도는 `Player`만 해당되니 `Player&`로 받기로 설계. 참조 vs 포인터 판단은 기존에 정리한 기준("호출 시점에 대상이 없을 수 있는가?")을 그대로 적용 — 전투 중엔 항상 유효한 대상이 있으므로 둘 다 참조가 맞다고 스스로 결론. `const` 여부도 "값을 변경해야 하니 비-const 참조"라고 정확히 판단함.

### 19. `TakeDamageHealth` 시그니처 리팩토링 — "this가 안 쓰이는 멤버 함수" 문제

**초기 설계**: `virtual void TakeDamageHealth(Character& _target, int _damage)`를 `Character`에 두고, 공격자 쪽에서 `_player.TakeDamageHealth(_target, damage)`처럼 호출.

**발견된 문제**: 함수 본문이 `_target.SetHealth(_target.GetHealth() - _damage);`만 하고 `this`(호출한 객체, 즉 공격자)는 전혀 안 씀. 그 결과 "누구에 대고 호출하든 상관없는" 함수가 됐고, 실제로 `CozySnake::Skill_1`에서 이미 `Player&`인 `_target`을 다시 `static_cast<Player&>(_target)`로 캐스팅하는 무의미한 코드까지 발생함 (컴파일은 되지만 아무 효과 없는 캐스트).

**리팩토링**: `virtual void TakeDamageHealth(int _damage)`로 바꾸고, **피격자 쪽에서 자기 자신에 대고 호출**하도록 변경(`_target.TakeDamageHealth(damage);`). `this`가 실제로 의미를 갖게 되어, 나중에 `Player`가 이 함수를 오버라이드해서(예: 방어구 효과 적용 등) 자기만의 피격 처리를 만들 수 있는 여지도 생김.

**리팩토링 중 놓쳤다가 잡은 실수**: `FirstTypeSkill::Execute`(플레이어의 특수 스킬 실행 로직)에서 새 시그니처로 바꾸면서 `_player.TakeDamageHealth(FinalSkillPower);`라고 잘못 호출함 — **플레이어가 몬스터를 공격하는 스킬인데 플레이어 자신이 피해를 입는 코드**가 된 것. 리뷰에서 발견되어 `_target.TakeDamageHealth(FinalSkillPower);`로 정정. 함수 시그니처를 바꿀 때는 그 함수를 호출하는 모든 지점을 다시 검토해야 한다는 걸 보여주는 사례.

### 20. `FirstTypeSkill::Execute` — 심각한 자기 자신 변형 버그

```cpp
case Type::Oblivion:
    SkillPower *= 2; // 버그: 지역 변수가 아니라 멤버 변수를 직접 곱함
```
`SkillPower`가 **멤버 변수**(스킬 고유의 기본 위력)인데, 상성 배율 계산에서 이 멤버 변수 자체에 곱셈/나눗셈을 적용해버려서, 스킬을 한 번 쓸 때마다 위력이 영구적으로 배가되거나 줄어드는 버그가 있었음. 이전에 `CozySnake::Skill_3`에서 겪었던 "저장된 상태를 계산에 직접 사용해서 매번 누적되는" 패턴과 같은 종류의 실수. `int FinalSkillPower = SkillPower;`라는 지역 변수를 도입해 그 지역 변수에만 배율을 적용하도록 수정 — 이번엔 리뷰 지적 없이 사용자가 다른 지적사항(min-damage 등)과 같이 스스로 알아채고 고침.

이 김에 다른 문제들도 같이 발견/수정됨:
- `srand(time(NULL))`을 `Execute()` 호출마다 실행하고 있었음 — 초 단위 해상도라 짧은 시간 안에 여러 번 호출하면 같은 시드로 재설정되어 "무작위" 값이 반복될 위험. `main()`에서 프로그램 시작 시 한 번만 호출하도록 이동.
- 상성 역배율(0.5배) 적용 시 정수 나눗셈으로 데미지가 0이 될 수 있는 문제 — `if (FinalSkillPower < 1) FinalSkillPower = 1;`로 최소 데미지 보장 추가 (`game_design.md`에 이미 명시돼 있던 규칙).
- 상성 약점 배율을 문서의 1.5배 대신 2배로 의도적으로 확정 — `game_design.md` 갱신.

### 21. `Player::BaseAttack`의 매개변수 — 포인터에서 참조로

`Player::BaseAttack(Character* _target)`으로 처음 선언했다가, 리뷰에서 "전투 중 대상은 항상 존재하니 참조가 맞지 않냐"는 지적을 받고 `Player::BaseAttack(Character& _target)`으로 수정 — 다른 데미지 관련 함수들과 일관성이 맞춰짐.

### 22. `GlobalSet.h`의 `Hypersomnia` — 4번째 특수 상태

기본 3속성(자각/몽환/망각)과는 별개로, 수면 심도가 100에 도달했을 때(하드모드) 진입하는 특수 상태를 나타내는 값이었음. 코드에 먼저 존재했으나 `game_design.md`엔 반영이 안 되어 있어 리뷰 중 발견 — 사용자 설명을 받아 8.3절로 신설, 향후 기본 속성과 무관한 별도 특수 능력을 부여할 예정이라는 것도 기록.

### 23. 스킬 정보 관리 방식 논의 — 데이터 테이블 vs 다형성 vs "스킬을 객체로"

몬스터 스킬(`CozySnake::Skill_1~3`)처럼 캐릭터의 메서드로 스킬을 구현하는 방식(다형성)과, 이전 프로젝트의 `EnemyDataManager`류 데이터 테이블 방식을 비교. 사용자가 "Base×Modifier 조합에 따라 스킬 종류가 많아질 것"이라고 판단해 **스킬을 독립된 객체로 만드는 방식(Command/Strategy 패턴)**을 선택 — `WeaponSkill`(순수 가상 `Execute` 인터페이스) + `FirstTypeSkill`(구체 구현) 구조로 이어짐.

이 과정에서 나온 추가 질문들과 답변:
- "가상 함수로 만든 이유가 뭐야?" → 호출부가 구체적으로 어떤 스킬 객체를 들고 있는지 몰라도 `Execute()`만 호출하면 되게 하기 위함 — `Room::EnterEvent`/`Monster::Action` 때와 동일한 원리임을 재확인.
- "그럼 구현은 어디 하는거야?" → 베이스(`WeaponSkill`)엔 구현이 없고, 파생 클래스(`FirstTypeSkill`)마다 각자 `.cpp`에 구현 — `Monster`/`CozySnake` 구조와 동일한 패턴임을 연결지어 이해함.
- "스킬마다 파일을 다 따로 만들어야 하나?" → 아니오, C++은 파일-클래스 1:1을 강제하지 않음. 더 중요한 건 "구조가 같고 수치만 다른 스킬"은 하나의 파라미터화된 클래스(생성자로 값만 다르게)로 재사용하고, "로직 자체가 다른" 스킬만 전용 클래스를 만드는 것 — 데이터 테이블 방식과 다형성 방식을 섞은 절충안. 사용자가 "추상화해서 구분하라는 거구나"라고 스스로 정리함.

### 24. `Weapon`의 `SynthesisType` 열거값 — 답변 및 해결

리뷰에서 두 차례 물었던 질문에 답변을 받음: `SynthesisType`(`Synthesis1`~`9`)은 초기 구현 아이디어였고, 사용자 스스로도 "조합 개수가 늘어날 걸 생각하면 좋은 방향이 아니다"라고 판단함. 다만 "Base 재료 습득 → Modifier 재료 습득 → 꿈조합으로 결합 → 유효한 조합이면 Synthesis 무기 생성 → 장착"이라는 게임 흐름상, Base/Modifier/합성결과라는 세 가지 "역할"은 필요하지 않냐는 질문이 나옴.

**결론**: 세 가지 역할이 필요한 건 맞지만, "합성 결과"는 별도의 enum 타입이 아니라 **`BaseType` 필드 + 속성(`Type`) 필드를 이미 갖고 있는 `Weapon` 객체 자체**로 표현하면 충분함 — 그 두 필드가 이미 "무엇의 조합인지"를 완전히 나타내므로, 그걸 또 다른 enum으로 재인코딩할 필요가 없음. Base나 속성 종류가 늘어나도 `Weapon` 클래스 자체는 안 바뀌고 각 enum에 값만 추가하면 됨. "유효하지 않은 조합도 있을 수 있다"는 부분은 별도의 (Base, 속성) 유효성 테이블로 처리하면 됨.

### 25. 합성 무기의 이름 표현 및 Modifier 아이템 재설계

**무기 이름**: `Monster`가 이미 `Name`/`Description`을 멤버로 갖고 있는 패턴을 그대로 재사용 — `Weapon`에도 `std::string Name`을 추가하고, 꿈조합이 일어나는 시점에 (Base, 속성) 조합을 유효성 테이블에서 찾아 이름을 채워 넣는 방식으로 결론. 유효성 검사와 이름 부여를 사실상 같은 데이터로 한 번에 처리할 수 있음.

**Modifier 아이템 재설계**: "Modifier가 `Type`과 1:1 대응이 아니고, 층마다 다양한 Modifier 아이템이 있으며 각각 4가지 속성 중 하나를 가진다"는 설명을 듣고, `ModifierItemType`도 `SynthesisType`과 똑같은 확장성 문제(아이템이 늘어날 때마다 enum 값 추가)를 겪을 것이라는 점을 짚음. 몬스터(적고 고유함 → 클래스)와 스킬(패턴이 겹치면 데이터) 논의 때와 같은 기준을 적용해, Modifier 아이템은 "이름+소속 층+속성 하나" 정도의 데이터 차이만 있어 보이므로 `struct ModifierItemData { Name, Attribute, FloorTheme }` + 데이터 테이블(이전 프로젝트의 `ItemDataManager` 패턴) 방식을 제안함 — 다음 세션에 실제 설계로 이어갈 예정.

**교훈**: "N개 유형이 있고 각 유형이 몇 개의 속성만 다르다"는 신호가 보이면, 매번 enum 값을 추가하는 대신 구조체+데이터 테이블로 옮길 신호로 보는 습관이 이제 여러 지점(몬스터 등급, 스킬, 합성 무기, Modifier 아이템)에서 반복적으로 적용되고 있음 — 처음엔 "일단 enum으로 다 만들어보고" 나중에 문제를 깨닫는 패턴이었는데, 이제 새 기능을 설계할 때 이 신호를 미리 알아채는 방향으로 발전 중.

## 지금까지의 핵심 교훈 정리

- **`switch`의 `break`는 `switch`문만 빠져나간다.** 바깥의 반복문(`while` 등)은 안 빠져나가므로, 반복문까지 종료하려면 `return`/`break`(라벨) 등을 명시적으로 써야 함.
- **다형성의 핵심은 "호출부가 구체 타입을 몰라도 되게 만드는 것"** — 타입별로 다른 처리가 필요하면, 호출부에서 타입을 판별하려 하지 말고 그 처리를 가상 함수 내부로 밀어 넣을 방법을 먼저 고민할 것.
- **참조 vs 포인터는 "대상이 없을 수 있는가/재바인딩이 필요한가"로 판단**, **const 여부는 "이 함수가 대상을 수정하는가"로 판단** — 서로 다른 축의 결정.
- **멤버 변수가 많아지면 생성자 없이 기본 생성 후 setter로 채우는 방식은 초기화 누락 실수를 유발하기 쉽다** — 필수 값은 매개변수 생성자로 강제하는 게 안전함.
- **쓰는 헤더는 항상 직접 include할 것** — 다른 헤더의 전이(transitive) include에 기대면 컴파일러/플랫폼이 바뀔 때 깨질 수 있음 (`<memory>`, `<algorithm>` 두 번 반복된 실수).
- **기획 문서(`game_design.md`)와 실제 코드가 어긋나면 그때그때 확인하고 문서를 갱신할 것** — 구현하다 보면 기획 당시 생각하지 못한 디테일이 나오는 게 자연스러우니, 발견 즉시 문서에 반영하는 습관이 중요.
- **상속 계층에는 "이 클래스가 무엇인가(정체성)"만 담고, "얼마나 강한가(등급)" 같은 분류는 멤버 필드로 표현할 것** — 등급을 상속으로 표현하면 정체성과 등급이 뒤섞여 계층이 난잡해지기 쉬움.
- **적은 수의 개성 있는 개체 vs 많은 수의 유사한 개체 — 이 전제에 따라 데이터 테이블 방식과 전용 클래스 방식 중 맞는 쪽이 갈린다.** 개체마다 고유 로직(스킬명, 특수 패턴)이 있다면 전용 클래스가, 스탯만 다르고 행동이 비슷하면 데이터 테이블이 더 잘 맞음.
- **기획이 자주 바뀌는 프로젝트에서는, 자주 바뀌는 부분(개별 이름/수치)일수록 코드에 늦게, 데이터로 분리해서 넣는 게 안전하다** — 시스템 구조부터 안정화하고 세부 콘텐츠는 나중에 채우면, 기획 개명/재설계가 있어도 코드 전체가 흔들리지 않음.
- **`private` 멤버는 파생 클래스에서도 이름으로 직접 접근할 수 없다.** 파생 클래스가 베이스의 데이터를 직접 건드려야 한다면 `protected`로 열어주거나, 베이스의 `public`/`protected` 함수를 통해서만 접근해야 함.
- **`override`는 이름과 반환 타입, 매개변수까지 베이스와 정확히 일치해야 인정된다.** 하나라도 다르면(오타 포함) 오버라이드가 아니라 컴파일 에러가 남 — 베이스 선언을 복사해서 시작하면 이런 실수를 줄일 수 있음.
- **필수 의존 대상(예: BattleArea의 몬스터)이 항상 있어야 한다면, 없는 상태로도 만들 수 있는 기본 생성자를 남겨두지 말 것.** 생성자를 강제하면 null 체크 코드 자체가 필요 없어짐 — 이미 확정된 상위 설계(고정 맵이라 방마다 내용물이 고정)와 클래스 설계를 연결지어 판단하면 이런 결정이 쉬워짐.
- **당장 쓰이지 않고 부작용까지 있는 함수는 "혹시 몰라서" 남겨두지 말고 지울 것.** 필요해지면 그때 다시 만들면 됨 — 미리 만들어두는 비용(혼란, 실수 유발)이 나중에 다시 만드는 비용보다 큰 경우가 많음.
- **멤버 함수인데 `this`를 전혀 안 쓴다면 설계를 의심할 것.** 그런 함수는 "누구에 대고 호출하든 결과가 같아지는" 함수라, 호출부 코드가 헷갈리기 쉽고(불필요한 캐스트 유발 등) 진짜 의도(누가 무엇을 하는가)를 흐림. 보통 "그 값을 실제로 갖고 있는 객체"에 대고 호출하도록 시그니처를 바꾸면 해결됨.
- **함수 시그니처를 바꾸면, 그 함수를 호출하는 모든 지점을 다시 확인할 것.** 한 곳만 고치고 다른 호출부를 놓치면, 컴파일은 되지만 의미가 완전히 뒤바뀐 코드(예: 공격자가 되레 피해를 입는 코드)가 조용히 남을 수 있음.
- **배율/증감 계산을 할 때, 계산 대상이 "멤버 변수 원본"인지 "지역 변수 사본"인지 항상 확인할 것.** 멤버 변수에 직접 곱셈/나눗셈을 적용하면 호출할 때마다 값이 누적/축소되어 영구히 오염됨 — 계산용 지역 변수를 따로 두고 그 위에서만 연산해야 함.
- **학습하고 싶은 기법이 있어도, 기능이 실제로 요구하지 않으면 억지로 끼워 넣지 말 것.** 기능 하나하나가 자연스럽게 요구하는 기법을 그때그때 배우는 게, 기법을 먼저 정하고 기능에 끼워 맞추는 것보다 코드 품질과 학습 효과 둘 다에 낫다.
